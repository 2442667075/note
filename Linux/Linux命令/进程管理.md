# jobs /fg/bg 笔记（终端前后台任务调度）

> 核心概念：**jobs/fg/bg 是 Shell 内置命令，仅管理当前 Shell 会话内的作业**。 区分：**作业号 `%1 %2`（仅当前 shell 有效） vs PID（系统全局进程号）**

## 作用

对当前终端 shell 中的作业进行查看、暂停、前后台切换，配套 wait/disown/kill 系列信号控制后台任务。

## 基础命令与快捷键

表格

|命令 / 快捷键|含义|
|---|---|
|`jobs`|查看当前 shell 所有作业（运行中 + 已停止）|
|`jobs -l`|列出作业，附带 PID|
|`jobs -r`|只列出**正在运行**的作业（Bash）|
|`jobs -s`|只列出**已停止**的作业（Bash）|
|`jobs -p`|输出作业对应的进程组 ID（Bash）|
|`Ctrl + z`|向前台进程组发送`SIGTSTP`，暂停前台作业，放入 shell 作业表（状态 Stopped）；程序可捕获 / 忽略此信号，不是 100% 生效|
|`bg %n`|恢复编号 n 的**已暂停作业**，在后台继续运行（background）|
|`fg %n`|把编号 n 的作业切回前台运行（foreground）|
|`kill %n`|通过**作业号**发送信号给 shell 作业；推荐带`%`避免和 PID 混淆；默认信号`SIGTERM`|
|`kill pid`|通过系统全局 PID 发送信号给进程|

> ✅ 规范写法：`bg %1`、`fg %1`、`kill %1`；虽然部分 shell 允许省略`%`，面试 / 脚本推荐写`%`消除歧义。

## 拓展控制命令（面试高频）

表格

|命令|作用|
|---|---|
|`command &`|启动命令，直接放到后台运行|
|`wait %1`|等待指定作业结束；`wait PID`等待指定子进程结束|
|`$!`|保存最近一次后台任务的 PID|
|`disown %1`|将作业从 shell 作业表移除；不再被 jobs 查看|
|`disown -h %1`|标记作业，shell 退出时**不发送 SIGHUP**（Bash 特有）|
|`kill -STOP PID`|发送`SIGSTOP`，强制停止进程；该信号**不可捕获、不可忽略**|
|`kill -CONT PID`|发送`SIGCONT`，恢复被停止的进程|

## 作业状态转换表

表格

|操作|任务状态 / 行为|
|---|---|
|`./test.sh`|前台运行|
|`./test.sh &`|后台直接启动运行|
|`Ctrl+Z`|发送 SIGTSTP，暂停前台作业 → Stopped|
|`bg %1`|恢复已暂停作业，后台持续运行 → Running|
|`fg %1`|后台作业切回前台运行|
|`kill %1`|默认发送 SIGTERM，请求进程正常退出（进程可捕获）|
|`kill -STOP PID`|发送 SIGSTOP 强制停止进程，不受程序捕获控制|
|`kill -CONT PID`|恢复被 SIGSTOP 暂停的进程|
|`wait %1`|阻塞等待指定作业执行完毕|

jobs 输出标记说明：

- `+`：默认作业，fg/bg 不带编号时优先选中这个任务
- `-`：下一个默认作业
- `Stopped`：作业暂停，**不会自动继续跑**
- `Running`：作业正在后台运行

## 实战案例

```
# 1. 前台运行脚本
./test.sh
# 2. Ctrl+Z 发送SIGTSTP，暂停任务，加入作业表（Stopped）
# 3. 查看当前shell全部作业（带PID）
jobs -l
# 4. 将1号暂停作业，后台恢复运行
bg %1
# 5. 将1号作业切回前台
fg %1

# 后台直接启动任务，并重定向日志（重点！后台默认输出会打印终端）
./test.sh >> test.log 2>&1 &
# 获取刚刚后台任务的PID
pid=$!
echo $pid

# 等待后台任务执行结束
wait $pid
echo "任务执行完成"

# disown 示例：后台启动后脱离shell作业管理
./long_task.sh &
disown %1

# kill信号控制进程
kill -STOP 1234   # 强制停止PID=1234进程
kill -CONT 1234   # 恢复PID=1234进程

# nohup：关闭终端后尽量保持运行，重定向标准输入到空设备
nohup ./test.sh >> test.log 2>&1 < /dev/null &
```

## ⚠️ 面试 & 实操易错细节

1. **Ctrl+Z ≠ 后台持续运行**`Ctrl+Z`发送`SIGTSTP`，只是暂停任务（Stopped），**不会继续执行**，必须执行`bg %n`才会在后台跑；程序可捕获 SIGTSTP，存在无法暂停的情况。
2. jobs 看到的作业，包含**运行中 + 停止**两种状态，不只是后台任务。
3. 关闭终端后后台作业**不一定会退出** Shell 退出时会向作业发送 SIGHUP；进程最终是否终止，取决于信号处理逻辑、Shell 配置。

> 单纯`bg`后台任务**不能保证关闭终端继续跑**。
> 
> - 临时长任务：`nohup`；交互式需要重连：`tmux/screen`；系统服务：`systemd`。

4. `disown`与`nohup`不是一回事

- disown：从 shell 作业表移除，或标记不接收 SIGHUP；**不会重定向 IO**
- nohup：让程序忽略 SIGHUP，自动处理输出；推荐配套 IO 重定向。

5. 后台任务 IO 坑 后台进程 stdout/stderr 默认绑定当前终端，日志会刷屏终端；**必须做重定向**，`>> log 2>&1`。
6. 信号区分

- SIGTERM（kill 默认）：友好退出，程序可捕获、做清理，也可忽略
- SIGSTOP：强制停止，**不能捕获、不能忽略**，只能用 CONT 恢复
- SIGKILL（kill -9）：强制杀死，不可捕获，尽量少用

|jobs -r / -s|只看运行中 / 停止作业|
|Ctrl+Z|SIGTSTP 暂停前台任务，加入作业表|

|暂停前台任务|Ctrl+Z|

|1 号作业切前台|fg %1|

## 面试要点总结

1. jobs/fg/bg 是 Shell 内置，**仅限当前终端会话**；作业号`%n`只在本 shell 有效，和全局 PID 分开。
2. `Ctrl+Z`是暂停（SIGTSTP），任务 Stopped，**bg 才会继续后台跑**。
3. `&`启动后台任务，IO 默认输出到终端，生产环境务必重定向 stdout/stderr。
4. wait 用于脚本并行任务，等待后台子进程完成；`$!`捕获后台任务 PID。
5. disown 和 nohup 作用不同；`kill -STOP`信号不可捕获，和 Ctrl+Z 的 SIGTSTP 有区别。
6. 普通 bg 后台任务，关闭终端不一定存活；持久运行分场景选择 nohup /tmux/systemd。



# kill 命令笔记（进程信号发送）

> 核心概念：kill**不只是杀死进程，本质是向进程发送信号**；优先使用信号名称写法，可移植性更强；仅 SIGKILL、SIGSTOP 两个信号不能被捕获、阻塞或忽略。

## 作用

向指定 PID/Shell 作业发送操作系统信号，实现优雅终止、暂停、恢复进程等操作。 语法：

```
kill [options] <pid> [...]
```

## 常用信号（**x86_64 Linux 常见编号，跨架构不保证完全一致，推荐优先写信号名**）

表格

|编号|信号名|说明|快捷键 / 场景|
|---|---|---|---|
|1|SIGHUP|挂断，终端断线；常用于让程序重载配置；nohup 可忽略该信号|终端退出时，shell 会向作业发送|
|2|SIGINT|中断，请求程序停止|`Ctrl + c`|
|3|SIGQUIT|退出，程序可生成 core dump 核心转储|`Ctrl + \`|
|15|SIGTERM|**默认信号**，优雅终止；允许程序清理资源、保存数据|`kill PID`默认发送 SIGTERM|
|9|SIGKILL|强制终止；**不可捕获、不可忽略**|仅 SIGTERM 无效时使用|
|18|SIGCONT|继续运行，恢复被暂停的进程；即使进程注册信号处理函数，依然会恢复进程|配合 SIGSTOP 使用，bg/fg 底层依赖此信号|
|19|SIGSTOP|强制暂停进程；**不可捕获、不可忽略**|`kill -STOP PID`|
|20|SIGTSTP|终端暂停，程序可捕获 / 忽略|`Ctrl+Z`触发|

## 参数说明

- `-l`：查看系统支持的信号列表
    - `kill -l`：列出全部信号名称
    - `kill -l SIGKILL`：查询指定信号对应的编号
    - `kill -l 9`：通过编号反向查询信号名

> 注意：kill 既是 shell 内置命令，也存在外部二进制实现，选项细节会随 shell / 系统略有差异

- `-s`：指定发送的信号，`kill -s TERM 1234`等价`kill -TERM 1234`

## 拓展配套命令

表格

|命令|作用|
|---|---|
|`kill -0 PID`|**不发送真实信号**；检测进程是否存在，同时检查当前用户是否有权限发送信号|
|`pgrep -a name`|查找匹配进程，同时打印命令行|
|`pgrep -a -u liangxu`|查看 liangxu 用户所有进程|
|`pkill -TERM -x program_name`|按进程名**精确匹配**，发送优雅终止信号|
|`pkill -u liangxu`|向指定用户所有进程发送默认 SIGTERM，风险较高|

## 实战案例

```
# 查看全部信号列表
kill -l
# 查询SIGKILL对应的编号
kill -l SIGKILL

# 优雅终止进程（推荐首选，优先用信号名写法）
kill -TERM 1234
# 强制杀死进程（慎用）
kill -KILL 1234

# 暂停进程
kill -STOP 1234
# 恢复暂停进程
kill -CONT 1234

# 检测进程是否存在&权限校验
kill -0 1234
echo $?   # 返回0：进程存在且有权限；非0：进程不存在/权限不足

# 按shell作业号发送信号（当前shell后台任务）
kill %1

# 查看进程PID、父PID、进程状态、程序名
ps -o pid,ppid,stat,comm -p 1234

# 精确匹配进程名，优雅终止
pkill -TERM -x nginx
```

## ⚠️ 面试 & 实操易错细节

1. **信号编号跨架构不一定相同，脚本尽量写信号名**`kill -STOP 1234` > `kill -19 1234`，可读性、可移植性更好。
2. 只有 **SIGKILL(9)、SIGSTOP(19)** 无法捕获、阻塞、忽略；其余信号程序都可以捕获、自定义处理逻辑。 SIGCONT 特殊：收到该信号一定会恢复已停止进程，不受进程信号处理函数影响。
3. SIGHUP 不是关闭终端就一定杀死后台进程 Shell 退出**可能**向作业发送 SIGHUP；进程最终是否退出取决于信号处理逻辑、会话关系、Shell 配置。`nohup`仅让程序忽略 SIGHUP，**不会把程序变成系统服务，无法保证永久运行**。
4. 批量杀进程坑点（思维导图原命令缺陷）

```
# ❌ 错误示例
kill -9 $(ps -ef | grep liangxu)
```

- ps 输出整行文本，不是单纯 PID；grep 自身进程也会被匹配，容易误杀。
- 按用户全量杀进程风险极高。 ✅ 规范做法：先用 pgrep 确认进程，确认无误后 pkill 精确匹配

```
pgrep -a -u liangxu
pkill -TERM -u liangxu -x program_name
```

5. kill -9 也有可能无法立刻回收进程（面试高频考点）

- D 状态（不可中断睡眠）：进程在内核态等待 IO，收到 SIGKILL 也不会立刻退出，需要等待内核 IO 完成。
- Z 状态（僵尸进程）：进程本身已经结束，仅父进程未回收退出状态；kill -9 对僵尸进程无效，要处理父进程。

6. 使用原则：**优先 SIGTERM，等待一段时间，进程无响应再考虑 SIGKILL**，kill -9 容易丢失内存数据、损坏文件。

表格

|强制终止进程|kill -KILL 1234|

## 面试要点总结

1. kill 的本质是**发送信号**，不是直接销毁进程；默认信号 SIGTERM (15)，给程序清理资源机会。
2. SIGKILL、SIGSTOP 是仅有的两个不能捕获 / 忽略的信号；脚本优先使用信号名而非数字编号。
3. kill -0 不发送真实信号，用来检测进程存活与权限。
4. kill -9 不是万能：D 状态进程要等内核 IO，僵尸进程只能处理父进程。
5. 批量杀进程先 pgrep 确认，尽量精确匹配进程名，避免全用户批量杀进程造成误删。
6. SIGCONT：恢复停止态进程，不受进程注册的信号处理函数影响。


# killall 命令笔记

> 作用：**根据进程名批量向进程发送信号**，不是直接杀死进程，底层原理同 kill。 对比：kill 按 PID 发送信号；killall 按进程名批量发送信号。 ⚠️ 重要提醒：killall 存在两个主流实现：**psmisc 版本（PC Linux）** 和 **BusyBox 版本（嵌入式开发板）**，参数、匹配规则不一样，一切以开发板 `killall --help` 为准。

## 语法

```
killall [参数] 进程名
```

## 常用参数

表格

|参数|作用|
|---|---|
|`-l`|列出当前 killall 支持的所有信号列表|
|`-u 用户名`|仅匹配指定用户下的进程，发送信号|
|`-s 信号名`|指定发送的信号，推荐使用信号名，可移植性更强|
|`-I`|进程名匹配忽略大小写|
|`-e` / `--exact`|精确匹配完整进程名；超长进程名可能因无法获取全名而跳过进程（psmisc 版本特性，BusyBox 不一定支持）|
|`-w`|等待所有目标进程退出，不适合做可靠超时等待|
|`-q`|静默模式，不输出 “未找到进程” 这类提示，行为随实现变化|
|`-r`|使用正则表达式匹配进程名，仅 psmisc 版本支持，BusyBox 一般无此选项|
|`-V`|打印 killall 版本信息，部分实现支持|

> 默认信号：`SIGTERM(15)`，优雅终止，允许应用执行资源释放、保存数据等清理逻辑。

## 实战示例（嵌入式推荐写法）

```
# 【安全操作习惯】先查看匹配到哪些进程，确认无误再发信号
pgrep -a sleep

# 优雅终止所有sleep进程（推荐首选）
killall -TERM sleep

# 查看killall支持的全部信号
killall -l

# 强制终止所有sleep进程（慎用！程序无法做资源清理，可能丢数据）
killall -KILL sleep

# 仅向harry用户下sleep进程发送优雅终止信号
sudo killall -TERM -u harry sleep

# 向harry用户下全部进程发送SIGTERM（高风险！会杀掉登录会话、后台任务等，谨慎执行）
sudo killall -u harry
```

## ⚠️ 重点注意（嵌入式开发板必看）

1. **进程名匹配规则随实现不同而变化** psmisc 版 killall 默认要求进程名完全一致，**不是包含字符串就匹配**；BusyBox 精简版行为又有差异。 👉 固定安全流程：**永远先用 `pgrep -a` 预览匹配进程，确认目标无误，再执行 killall**。

> 如果需要按完整命令行匹配进程，使用 `pgrep -f`。

2. **BusyBox 工具集的坑** 开发板上有没有`killall`/`pkill`/`pgrep`，**取决于编译 rootfs 时是否开启对应 applet**，不能默认一定存在。 开发板上检查命令是否可用：

```
# 查看busybox编译包含的工具
busybox --list | grep -E '^(kill|killall|pkill|pgrep)$'
# 检查命令是否存在
command -v killall
command -v pkill
# 查看当前版本支持哪些参数
killall --help
```

如果板子无 killall，优先用 pkill；pkill 也没有，则用`ps + grep`提取 PID 配合 kill 操作。

3. 即使发送 SIGKILL，进程也不一定立刻消失

- D 状态（不可中断睡眠）：进程在内核态等待 IO，收到 SIGKILL 也要等内核 IO 完成后才退出。
- Z 状态（僵尸进程）：进程本身已经退出，父进程未回收资源，killall 对僵尸进程无效。

4. 跨平台差异 killall 在非 Linux 系统语义完全不同，嵌入式开发**只在目标板上使用**，不要直接把 PC 上的 killall 脚本直接移植到其他类 Unix 系统。

## killall、kill、pkill 简要对比

表格

|命令|匹配依据|特点|嵌入式场景|
|---|---|---|---|
|kill|PID|单个进程发送信号，所有系统必带|精准控制单个进程，开发板通用|
|killall|进程名|批量匹配，参数受 psmisc/BusyBox 版本影响|批量操作同名进程，裁剪 rootfs 可能没有|
|pkill|进程名 / 命令行|功能类似 killall，BusyBox 更常编译进这个 applet|嵌入式板子优先备选方案|

## 面试背诵要点

1. killall 作用：**按进程名批量发送信号，默认 SIGTERM 优雅退出**。
2. 安全规范：先`pgrep -a`预览进程，确认目标后再执行，避免误杀。
3. 版本差异：PC 是 psmisc 版；嵌入式开发板是 BusyBox 版，支持的参数不一样，以`--help`为准。
4. BusyBox 是否有 killall/pkill 取决于编译选项，不能假定板子自带。
5. SIGKILL 强制终止慎用；D 状态进程收到 SIGKILL 也无法立刻退出。

## 易错坑总结

```
# ❌高危命令：杀死指定用户下全部进程，会干掉终端、业务服务等，不要随便执行
sudo killall -u harry
```



# ohup 命令笔记

> 作用：让进程忽略 SIGHUP 信号；串口 /ssh 终端关闭时，进程不会退出，常配合`&`后台运行。 注意：`nohup`本身**不负责后台运行**；`&`才是放到后台，二者经常搭配使用。

## 语法

```
nohup 命令 [参数]
```

## 实战示例

```
# nohup + & 组合：后台运行程序，关闭终端不退出
nohup ./test &

# 将标准输出、标准错误全部重定向到file.txt
nohup ./test > file.txt 2>&1 &
```

## 基础说明

1. 默认行为：不手动重定向时，程序输出默认保存到当前目录 `nohup.out`。
2. `2>&1`含义：把标准错误 (2) 合并到标准输出 (1)，统一写入目标文件。

## ⚠️ 嵌入式 Linux 重点注意

1. 仅屏蔽 SIGHUP：**不能防止程序崩溃、kill 信号、板子断电**。程序收到 SIGTERM、SIGKILL 依旧会退出。
2. BusyBox 支持：裁剪 rootfs 是否带 nohup，取决于编译 applet；开发板上可通过`command -v nohup`检查。
3. 和`&`的区分
    - `&`：放到 shell 后台，**一旦关闭终端，会发送 SIGHUP 杀死进程**
    - `nohup`：让进程忽略 SIGHUP，脱离终端挂断信号影响
4. 日志文件：长时间运行业务程序，注意日志持续写入导致存储占满，嵌入式 flash 空间有限，需要考虑日志轮转。

## 面试背诵要点

1. nohup 核心：让进程忽略 SIGHUP 信号；**& 才是后台运行**，两个命令作用不一样，经常一起搭配。
2. 不重定向输出，默认日志写入 nohup.out。
3. nohup 不能抵御 SIGTERM/SIGKILL，只是解决关闭终端进程被杀的问题，**不是守护进程**。

## 易错坑

- ❌误区：nohup = 后台运行程序
- ✅正确：nohup 负责忽略挂断信号，`&`实现后台执行。单独写 nohup 不带 &，程序依旧在前台阻塞终端。

# nice/renice 命令笔记

> 作用：调整进程调度优先级 区分：`nice` **启动进程时设置 nice 增量**；`renice` **修改已经正在运行进程的 nice 值** 核心概念：nice 值范围 `-20 ~ 19`
> 
> - `-20`：普通调度下权重最高
> - `19`：普通调度下权重最低
> - 默认新建进程 nice 值继承父进程，shell 默认 nice 为 0

## 语法

```
nice [参数] [命令]
renice [参数] [目标]
```

## 参数

### nice

- `-n`：指定 nice 增量，**相对于父进程的 nice 值增加 N**，最终值会被限制在`-20 ~ 19`区间内

### renice

- `-g`：指定进程组 ID，修改整个进程组 nice 值
- `-p`：指定 PID，修改单个运行进程（常用）
- `-u`：指定用户名，修改该用户所有进程 nice 值

## 实战示例

```
# 启动vim，nice增量15，父shellnice为0时最终nice=15，放到后台运行
nice -n 15 vim &
# 简写写法，等价上面，增量+15
nice -15 vim &

# 修改PID=5200进程，nice设置为6
renice 6 -p 5200

# 将用户liangxu所有进程nice设置为-5（需要root权限）
renice -5 -u liangxu

# 查看指定进程nice值
ps -o pid,ni,pri,comm -p 5200

# 将PID5200进程nice调整为10
renice 10 -p 5200

# 启动低优先级后台任务
nice -n 10 ./background_task &

# 查看进程调度策略与实时优先级
chrt -p 5200
```

## ⚠️ 嵌入式 Linux 重点注意

1. nice -n N 是增量，不是直接设定最终值。父进程 nice 不为 0 时，最终 nice = 父 nice + N，上限 19，下限 - 20。
2. 普通用户权限：**只能调大 nice 值（降低进程 CPU 权重）；调小 nice 值（提升权重）需要 root 权限**。renice 参数顺序在不同实现存在差异，以目标板`man renice`或`--help`为准。
3. nice/renice 主要影响普通调度策略下进程的 CPU 调度权重；现代 Linux 内核普通调度器实现随内核版本变化。chrt 可修改调度策略（SCHED_FIFO/SCHED_RR），**即使使用实时策略也不等于满足硬实时**，硬实时还受中断延迟、内核配置、优先级反转等因素影响。
4. BusyBox 裁剪系统：部分精简 rootfs 可能不带 nice/renice，开发板使用前检查：`command -v nice`。
5. PRI 和 NI 不是同一个概念。NI 是 nice 值；PRI 是工具展示的调度相关字段，含义受调度策略与工具实现影响。

## nice/renice 与 chrt 区分（嵌入式面试高频）

- nice/renice：调整普通调度任务的 CPU 调度权重。适合降低日志压缩、后台计算等非紧急任务对 CPU 的竞争。
- chrt：查看或设置调度策略，例如 SCHED_FIFO、SCHED_RR。适用于需要实时调度特性的任务；配置不当会造成 CPU 卡死，需要谨慎使用。

> SCHED_OTHER 普通调度策略 和 SCHED_FIFO、SCHED_RR 实时策略属于不同调度类别，不能简单理解 nice 就是低优先级，chrt 就一定是硬实时。

## 面试背诵要点

1. nice：**启动进程时增加 nice 增量**；renice：修改**已经运行**进程的 nice 值。
2. nice 范围 `-20 ~ 19`；数值越小，普通调度下 CPU 权重越高。
3. 普通用户通常只能把进程 nice 值调大；提高优先级需要 root 权限。
4. nice 只是普通调度权重调整，**不是硬实时机制**；需要实时调度特性使用 chrt。

## 易错坑

```
# ❌误区：nice -n 15 直接固定最终nice等于15
# ✅正确：是在父进程nice基础上+15，结果限制在-20~19
```



# top 命令笔记

> 作用：实时显示进程动态、CPU、内存等系统资源占用情况

## 语法

```
top -hv|-bcEHiOSs1 -d secs -n max -u|U user -p pid -o fld -w [cols]
```

## 参数

- `-d`：指定屏幕刷新间隔，单位秒
- `-c`：**启动 top 时直接开启完整命令行显示**
- `-p`：指定 PID，只监控单个或多个进程状态（BusyBox 版本不一定支持）
- `-n`：设置信息更新最大次数，到达次数后 top 自动退出

## 快捷键（top 运行时按下）

- `c`：**切换**简短命令名 / 完整命令行显示模式
- `P`：按 CPU 使用率排序（大写 P）
- `M`：按物理内存使用率排序（大写 M）
- `1`：展开显示每个 CPU 核的负载状况（部分精简版不支持）

## 字段说明

表格

|字段|含义|
|---|---|
|PID|进程 ID|
|NI|nice 值|
|VIRT|进程使用或映射的虚拟地址空间大小|
|RES|当前驻留在物理内存中的页面大小，可能包含共享页面|
|%CPU|进程的 CPU 使用率，统计口径依实现和模式而异|
|%MEM|驻留内存占系统物理内存的比例，常见于 procps 版 top|

> 注意：RES 不等于进程独占的物理内存。精确分析内存可查看 `/proc/PID/smaps` 的 Pss、Private_* 字段。

## 实战示例

```
# 默认启动，实时查看系统进程动态
top

# 启动top直接显示完整命令行
top -c

# 设置刷新间隔2秒
top -d 2

# 总共刷新5次后自动退出
top -n 5

# 仅监控PID=1877进程，多PID写法 top -p 1877,1880（支持性依版本而定）
top -p 1877
```

## ⚠️ 嵌入式 Linux 重点注意

1. `top -c` 是启动时启用完整命令行；运行时按`c`是切换显示模式。完整命令行**不一定是可执行文件绝对路径**，受内核与工具实现限制。
2. BusyBox 的 top 和 PC 上 procps 版 top**功能差异很大**。`-p`参数在部分裁剪开发板不支持，所有语法以目标板`top --help`为准。
3. 故障排查思路
    - CPU 占用异常：按 P 排序，定位高占用进程；支持则按`1`查看多核负载，结合日志 /perf 进一步定位。
    - 内存持续增长：按 M 排序观察 RES 变化。RES 持续增长仅为线索，**不能直接判定内存泄漏**，需要搭配内存分析工具。
    - 系统卡顿：查看负载、CPU 空闲、内存与 Swap。Load Average 不等于 CPU 使用率，D 状态不可中断睡眠任务也会拉高负载。

## 面试背诵要点

top 用于动态查看系统进程、CPU 和内存使用情况。常见参数包括 `-d` 指定刷新间隔、`-n` 指定刷新次数、`-p` 指定监控 PID（视实现而定）。交互界面中，P 按 CPU 使用率排序，M 按内存排序，`1` 查看各 CPU 核心的统计信息。嵌入式 Linux 中，BusyBox 版 top 的功能可能比 procps 版精简，应以目标系统实际支持的参数为准。

## 易错坑

- `top -c` 和交互快捷键`c`作用不完全相同：一个是启动时开启，一个是运行中切换。
- RES 包含共享内存页面，**不是进程独占物理内存**。
- 嵌入式极简 rootfs 可能不带 top，静态查看进程改用 ps。

# ps 命令笔记

> 作用：静态获取进程状态快照（和 top 区分，top 是实时刷新）

## 语法

```
ps [options]
```

## 参数

- `-e`：选中**所有进程**，等价 `-A`
- `-a`：选中关联终端的进程，包含其他用户的终端进程
- `-x`：扩展选择范围，可选中**无控制终端**的进程
- `-f`：完整格式输出进程信息
- `--forest`：树形展示父子进程关系
- `-u <用户名>`：按有效用户筛选进程，使用用户风格输出

> 查看进程环境变量不使用 ps，读取 `/proc/PID/environ`

## 信息说明

表格

|字段|含义|
|---|---|
|USER|进程所属用户|
|PID|进程号|
|PPID|父进程号（ps -ef 可看到）|
|%CPU|进程占用 CPU 百分比|
|%MEM|进程占用内存百分比|
|VSZ|虚拟内存大小|
|RSS|实际驻留物理内存大小（含共享页面）|
|TTY|进程绑定终端；无终端显示`?`|
|STAT|进程状态|
|START|进程启动时间|
|TIME|进程占用 CPU 总时间|
|COMMAND|执行程序命令|

**STAT 进程状态**

- R：运行 / 就绪，在运行队列
- S：可中断睡眠，等待事件，可以响应信号
- D：不可中断睡眠，等待内核操作；收到 SIGKILL 也不会立刻退出，需等待内核操作完成
- T：停止，作业控制暂停或调试暂停
- Z：僵尸进程，程序已退出，PCB 等待父进程 wait 回收；kill 无法直接杀死僵尸进程

> STAT 还附带辅助标记：s 会话首进程、l 多线程进程、+ 前台进程组，入门优先掌握 R/S/D/T/Z

## 实战示例

```
# BSD风格，查看系统所有进程资源信息（最常用）
ps aux

# Unix标准风格，查看所有进程+完整格式，带PPID
ps -ef

# 树形展示父子进程（需要支持--forest）
ps -ef --forest

# 查看指定PID的关键信息（嵌入式调试高频）
ps -p 1234 -o pid,ppid,stat,comm

# 指定字段输出，按CPU降序（GNU扩展，BusyBox一般不支持）
ps -eo pid,comm,%cpu,%mem --sort=-%cpu

# 指定字段输出，按内存降序（GNU扩展，BusyBox一般不支持）
ps -eo pid,comm,%cpu,%mem --sort=-%mem

# 查找ssh相关进程
ps aux | grep ssh

# 查看用户liangxu进程
ps -u liangxu

# 分页查看
ps aux | less
```

## ⚠️ 嵌入式 Linux 重点注意

1. 两套参数风格：`ps aux` BSD 风格，`ps -ef` Unix 标准风格，不要混用。
2. BusyBox ps 裁剪精简，**不支持`-eo`、`--sort`、`--forest`**等 GNU 扩展选项，以板子`ps --help`为准。
3. D 状态进程：一般是等待内核 IO 操作。发送 SIGKILL 也不能立刻退出，优先查看内核日志、驱动、文件系统，不要反复 kill。
4. 僵尸进程 Z：kill 无法直接清除，由父进程调用 wait 回收；父进程退出后由 init 进程回收。
5. `ps aux | sort -rnk 3` 会把表头一起参与排序；GNU 环境优先使用`--sort`参数。
6. 查找进程还可用 pgrep（部分开发板不带 pgrep）：`pgrep -a sshd`

## 面试背诵要点

ps 用于获取进程静态快照；top 用于动态观察进程与系统资源。 `ps -ef`、`ps aux`是最常用命令，分属两种选项风格。 `-e`选中全部进程，`-f`完整格式，`--forest`树形展示父子进程。 R/S/D/T/Z 分别代表运行就绪、可中断睡眠、不可中断睡眠、停止、僵尸。 僵尸进程不能通过 kill 直接消除；D 状态进程收到 SIGKILL 也可能无法立刻退出。 BusyBox 的 ps 缺少 GNU 扩展选项，实际使用以目标板支持情况为准。

## 易错坑

- ps `-e` **不是查看环境变量**，查看进程环境变量读取 `/proc/PID/environ`
- `-x` 的作用是选中无终端进程，不是简单输出更多信息
- `--forest`才是树形，`-f`只是完整格式，不是树形显示
- `ps aux | sort`会把表头一并排序，GNU ps 推荐`--sort`

# pstree 命令笔记

> 作用：以树状图展示进程父子派生关系，直观查看进程 fork 结构

## 语法

```
pstree [参数]
```

## 参数

- `-a`：显示命令行参数；不保证输出可执行文件绝对路径，取决于进程信息与工具实现
- `-c`：关闭同名进程精简合并，全部独立展开展示
- `-G`：使用 VT100 绘图字符绘制树形连线
- `-h`（psmisc 版本）：高亮当前进程及其祖先路径；高亮效果受终端、版本影响
- `-p`：输出树形结构，附带每个进程 PID（调试最常用）
- `-u`：显示进程所属用户名

## 实战示例

```
# 默认，树状展示所有进程，同名进程合并
pstree

# 树状图同时打印PID（嵌入式调试高频）
pstree -p

# 从PID=1234进程开始，显示PID与命令行参数（psmisc支持）
pstree -ap 1234

# 树状图同时显示进程所属用户
pstree -u
```

## ⚠️ 嵌入式 Linux 重点注意

1. **BusyBox 默认一般不带 pstree**，很多精简 rootfs 没有这个命令。
2. 备选方案 `ps axf`：仅 procps-ng 版本支持树形输出；BusyBox ps 大概率不支持`f`树形选项。 极简板子无树形工具时，读取 `/proc/PID/status` 的 PPid 字段手动追溯父子进程。
3. 使用场景：排查 fork 子进程、守护进程、僵尸进程的父子关系；pstree 只可视化结构，无法直接定位僵尸进程根源，需要搭配 ps 查看 STAT 状态。

## 面试背诵要点

pstree 用树状结构展示进程之间的父子关系。常用参数有 `-p` 显示 PID、`-a` 显示命令行参数、`-u` 显示用户信息。嵌入式 Linux 的精简 rootfs 可能没有 pstree，可以尝试用 ps axf 查看树形关系，或通过 `/proc/PID/status` 中的 PPid 追踪父进程。

## 易错坑

- `-a` 只展示命令行参数，**不一定输出程序绝对路径**。
- `ps axf` 不是所有平台都支持，嵌入式板子优先`ps --help`确认参数。
- 不能只依靠 pstree 判断僵尸进程，需要 ps 查看 STAT 状态。

# pgrep 命令笔记

> 作用：检索正在运行的进程，按名字 / 命令行匹配输出 PID，简化`ps | grep`的写法

## 语法

```
pgrep [参数] [匹配模式]
```

## 参数

- `-d`：设置多个 PID 输出之间的分隔符，默认换行；推荐写法`pgrep -d ' ' sshd`
- `-f`：匹配**完整命令行**；不加`-f`仅匹配进程名
- `-l`：同时列出 PID + 进程名
- `-a`：同时列出 PID + 完整命令行（注意：与 pstree `-a`含义不同，同字母参数功能不一定一致）
- `-u USER`：筛选**有效用户**的进程
- `-U USER`：筛选**真实用户**的进程（权限排查场景才需要区分）
- `-x`：进程名**严格完全匹配**，procps-ng 版本支持

> 匹配规则：pgrep 默认对**进程名**使用扩展正则，通常要求模式匹配整个进程名；加上`-f`后才切换为匹配整条命令行。

## 实战示例

```
# 查找sshd进程，只输出PID
pgrep sshd

# PID之间用空格分隔（参数放前面，推荐写法）
pgrep -d ' ' sshd

# 查找有效用户liangxu下的sshd进程PID
pgrep -u liangxu sshd

# 输出PID+进程名
pgrep -l sshd

# 精确匹配进程名
pgrep -x sshd

# 查找有效用户liangxu，精确匹配sshd，同时展示命令行
pgrep -a -u liangxu -x sshd

# -f 匹配完整命令行（包含参数）
pgrep -f ssh
```

## Shell 脚本实战场景

```
# 判断sshd进程是否在运行
if pgrep -x sshd >/dev/null; then
    echo "sshd is running"
else
    echo "sshd is not running"
fi
```

> 注意：pgrep 查到进程仅代表进程存在，**不等于服务正常可用**；判断和后续操作之间存在进程退出竞态问题。

## ⚠️ 嵌入式 Linux 重点注意

1. BusyBox 是否自带 pgrep 取决于编译时是否开启对应 applet；很多精简 rootfs 不带 pgrep。 查看板子是否支持：
    
    ```
    command -v pgrep
    busybox --list | grep '^pgrep$'
    ```
    
2. 无 pgrep 替代写法：`ps | grep '[s]shd'`，`[s]shd`防止 grep 自身被检索出来；缺点是依赖 ps 输出格式，稳定性弱于 pgrep。
3. 返回码：找到进程返回`0`；无匹配进程返回非 0，适合脚本判断。

## 面试背诵要点

pgrep 用于按进程名查找进程，支持正则表达式，可以配合 `-f` 匹配完整命令行、`-u` 筛选有效用户、`-l` 显示进程名、`-d` 指定 PID 分隔符。常见版本还支持 `-x` 精确匹配进程名。找到匹配进程时通常返回状态码 0，没有匹配时返回非 0。嵌入式 Linux 中要注意 BusyBox 的功能裁剪。

## 易错坑

- 默认只匹配**进程名**，不是命令行；`-f`才匹配整条命令。
- `-u`有效用户，`-U`真实用户，普通场景记住`-u`即可。
- `-a`参数和 pstree 的`-a`含义不一样，不要混淆。
- BusyBox pgrep 为可选编译项，不能默认板子一定存在。

# pmap 命令笔记

> 作用：查看进程虚拟地址空间的内存映射，用于分析进程内存分布、动态库加载、堆 / 栈映射，辅助内存异常排查

## 语法

```
pmap [参数] [进程ID]
```

## 参数

- `-x`：扩展详细输出，展示 RSS、Dirty 等内存统计，内存排查**必须掌握**
- `-d`：显示设备主次号、文件偏移等底层映射信息，了解即可
- `-q`：安静模式，不输出末尾内存汇总行，入门可暂不记忆
- `-V`：打印 pmap 版本信息后退出，知道即可

## 实战示例

```
# 查看PID=2775进程基础内存映射，查看加载的库、堆栈区域
pmap 2775

# 扩展详细模式，查看RSS、Dirty，内存分析首选
pmap -x 2775

# 快速查看进程整体内存概况（推荐，读取/proc文件）
grep -E 'VmSize|VmRSS|VmData|VmStk|VmSwap' /proc/2775/status

# 内核支持时，查看内存汇总统计，包含PSS、Private Dirty
cat /proc/2775/smaps_rollup
```

## 关键字段说明（pmap -x /proc 文件）

- Address：虚拟内存起始地址
- Kbytes：虚拟内存大小（虚拟地址空间，不等于物理内存）
- RSS：驻留物理内存页面总量，**包含共享库页面**
- PSS：共享页面按比例分摊后的内存，更适合评估进程实际内存占用
- Private Dirty：进程私有、已修改的驻留页面，内存增长排查重点指标
- Dirty：已修改页面相关统计；文件映射脏页可回写文件，匿名内存（堆）脏页和交换机制相关，**不能直接等同于内存泄漏量**
- Mode：内存权限（r/w/x/s/p 共享 / 私有）
- Mapping：映射对象，如 so 库、可执行文件、`[heap]`堆、`[stack]`栈

## ⚠️ 嵌入式 Linux 重点注意

1. BusyBox 是否包含 pmap 取决于编译选项；无 pmap 时：
    
    - `/proc/PID/maps`：查看内存映射地址、权限、映射对象，**仅映射关系，缺少 RSS/Dirty 统计**
    - `/proc/PID/smaps`：获取逐区域完整内存统计
    - `/proc/PID/smaps_rollup`：内核支持时，获取汇总内存数据
    
    > maps 只能替代查看映射关系，**不能完全等价于 pmap -x**。
    
2. 内存泄漏判断：**不能仅凭 [heap] 段 RSS 上涨直接判定泄漏**。内存分配器会缓存释放内存复用；大块分配可能使用独立 mmap 匿名映射，不一定落在`[heap]`。需要持续观察 RSS、匿名内存整体变化，再结合分配器统计、日志定位泄漏。
3. 适用场景：查看进程加载了哪些动态库、堆栈大小，辅助定位内存持续增长问题。

## 面试背诵要点

pmap 用于查看进程的虚拟内存映射。常用 `-x` 查看扩展内存统计，包括映射大小、RSS 和 Dirty。RSS 包含共享页面，不等于进程独占内存；需要更详细的信息时，可以查看 `/proc/PID/smaps`，并关注 PSS 和 Private Dirty。嵌入式 Linux 如果没有 pmap，可以使用 `/proc/PID/maps` 查看映射关系，或读取 smaps 获取详细统计。

## 易错坑

- Kbytes 是虚拟内存大小，不是实际物理内存占用。
- RSS 包含共享页面，多个进程共享同一个 so 库会重复统计，PSS 更精准。
- 不能单看`[heap]`RSS 判断内存泄漏；匿名 mmap 也会占用内存。
- `/proc/PID/maps`只保存映射信息，**没有 RSS/Dirty 统计，不等同 pmap -x**。

# lsof 命令笔记

> 作用：列出进程已经打开的文件（Linux 一切皆文件：普通文件、目录、socket 套接字、管道、设备文件等），常用于查找文件占用、端口占用、删除文件后磁盘空间不释放问题

## 语法

```
lsof [参数] [文件]
```

## 参数

表格

|优先级|参数|作用|
|---|---|---|
|必须掌握|`-p PID`|按进程 ID，列出指定 PID 打开的文件|
|必须掌握|`-u USER`|按用户 / UID 筛选进程打开的文件|
|必须掌握|`-i :PORT`|查询网络套接字，排查端口占用|
|必须掌握|`+d <目录>`|查看目录下被打开文件，**不递归子目录**|
|必须掌握|`+D <目录>`|递归查看目录及其子目录下所有被打开文件|
|建议掌握|`-a`|多个筛选条件**与（AND）逻辑**；不加 - a 默认是或（OR）逻辑|
|建议掌握|`-nP`|`-n`不解析主机名，`-P`不转换端口为服务名，加速网络排查输出|
|知道即可|`-c <进程名>`|按程序名列出进程打开文件|
|知道即可|`-d <文件描述符>`|列出占用该 fd 的进程|
|知道即可|`-g <PGID>`|按**进程组 ID**筛选（不是用户组 GID）|

## 实战示例

```
# 查看系统全部打开文件（输出量大）
lsof

# 查看/home目录下被打开文件，不递归子目录
lsof +d /home

# 递归查看/home所有子目录被打开的文件
lsof +D /home

# 查看哪个进程正在占用/bin/bash
lsof /bin/bash

# 列出liangxu用户打开的所有文件
lsof -u liangxu

# 列出bash程序打开的文件
lsof -c bash

# 查看PID=1930进程打开的文件
lsof -p 1930

# 根据文件描述符fd=1查找对应进程
lsof -d 1

# 组合条件：liangxu用户的网络套接字（-a开启AND逻辑）
lsof -a -u liangxu -i

# 查找TCP 80端口套接字
lsof -iTCP:80
# 查找TCP 80端口监听套接字
lsof -iTCP:80 -sTCP:LISTEN
# 不解析主机名、服务名，快速查看端口占用
lsof -nP -iTCP:80

# 查找已经rm删除，但进程仍持有句柄的文件（磁盘空间不释放场景）
lsof +L1
```

## ⚠️ 嵌入式 Linux 重点注意

1. BusyBox 默认不带 lsof，属于可选工具，很多精简 rootfs 没有预装。
    - 部分替代方案：`ls -l /proc/1930/fd`，仅查看**单个进程**的文件描述符，不能实现全系统按端口 / 目录 / 用户批量筛选。
    - 网络端口替代：`ss -lntp`，同样依赖系统工具与内核接口。
    - 权限限制：查看其他进程 fd 需要 root；容器、命名空间会进一步限制访问。
2. 需要 root 权限才能查看全部进程打开文件；普通用户仅能查看自身进程。
3. 经典调试场景：
    - 文件 rm 后磁盘空间不释放：文件硬链接删除，但进程仍持有 fd；等进程关闭 fd 后空间才回收。
    - 端口占用：定位占用端口的进程。

## 面试背诵要点

lsof 用于查看进程打开的文件，包括普通文件、设备文件、管道和网络套接字。常用 `-p` 按 PID 筛选，`-u` 按用户筛选，`-i` 查询网络套接字，`+d` 和 `+D` 分别用于非递归和递归目录查询，`-a` 用于组合筛选条件。它可以帮助排查端口占用，以及文件删除后空间仍未释放的问题。嵌入式系统若没有 lsof，可以根据需求使用 `/proc/PID/fd`、ss 等工具替代部分功能。

## 易错坑

- `+d`（不递归）、`+D`（递归）不要搞混。
- `-g` 筛选**进程组 PGID**，不是用户组 GID。
- 多条件组合不加 `-a` 是 OR 逻辑，容易筛选出不符合预期结果。
- `/proc/PID/fd`只能看单个进程 fd，**无法完全替代 lsof 全部功能**。


# pkill 命令笔记（

> 作用：按**进程名 / 属性**给进程发送信号（和 pgrep 配套；pgrep 查 PID，pkill 直接发信号） 区分：kill 根据 PID / 作业号发信号；pkill 根据筛选条件匹配进程再发信号；pgrep 只查询 PID 不发信号

## 语法

```
pkill [参数] 进程名
```

## 参数

表格

|优先级|参数|作用|
|---|---|---|
|必须掌握|`-signal`|指定信号，如 `-9`（SIGKILL 强制终止）、`-15`（SIGTERM 优雅退出，默认）|
|必须掌握|`-f`|对完整命令行使用扩展正则匹配，不是简单字面字符串匹配；正则特殊字符需要转义，**建议先用 pgrep 预校验匹配结果**|
|必须掌握|`-u USER`|筛选指定用户的进程；风险极高，会匹配该用户全部进程，仅了解用法，不随意执行|
|了解即可|`-x`|进程名**完全精确匹配**|
|了解即可|`-g PGID`|按进程组 PGID 发送信号|

> 默认信号：**SIGTERM(15)**，优先用这个让程序优雅退出；程序无法正常退出时，再考虑 `-9`

## 实战示例（XShell 直接复制运行）

```
# 向所有名为bash的进程发送默认15号信号（优雅关闭）
pkill bash

# 强制终止所有bash进程（SIGKILL 9）
pkill -9 bash

# -f 使用命令行正则匹配，建议先用pgrep校验匹配到哪些进程
pgrep -af "./myapp"
pkill -f "./myapp"

# 精确匹配进程名
pkill -x sshd

# 【了解，禁止随意执行】筛选指定用户进程，先查看再操作，存在竞态风险
pgrep -a -u liangxu
```

## ⚠️ 嵌入式 Linux 重点注意

1. pkill 和 pgrep 属于同系列工具（procps-ng），BusyBox 是否自带取决于编译选项，很多精简板子没有。
    
    - **安全替代方案**：加上`xargs -r`，无匹配进程时不执行 kill（`-r`依赖平台支持）
    
    ```
    pgrep -x myapp | xargs -r kill
    ```
    
2. 风险提醒：
    - `SIGKILL(-9)`进程无法捕获、无法执行自定义清理逻辑；内核依旧会回收进程基础资源。风险是应用来不及刷新缓冲区、保存业务数据，可能造成数据丢失或业务状态不一致，**优先 -15**。
    - `-f`使用正则匹配，`.`、`*`属于正则特殊字符，容易意外匹配其他进程，**务必先用 pgrep 校验**。
    - 检查进程和执行 pkill 之间存在竞态：进程列表可能发生变化。
3. 返回码：找到匹配进程返回 0；无匹配进程返回非 0，适合 shell 脚本判断。

## 面试背诵要点

pkill 根据进程名和筛选条件向进程发送信号，常见实现默认发送 SIGTERM。-f 按完整命令行正则匹配，-u 按用户筛选，-x 用于精确匹配进程名，-g 按进程组 ID 筛选。优先使用 SIGTERM 让程序正常退出，必要时才使用 SIGKILL。嵌入式 Linux 中，是否支持 pkill 取决于工具集及编译配置。

## 易错坑

- `-f`是正则匹配整条命令行，不是简单字符串匹配，记得先用 pgrep 验证。
- `-9`不能被进程捕获，程序无法做应用层清理，不推荐首选。
- `-u USER`范围很大，会匹配该用户所有进程，慎用。
- `pgrep | xargs kill`在无匹配进程时，部分平台依然会执行 kill，推荐带`xargs -r`版本。



# strace 命令笔记

> 作用：**跟踪进程的系统调用、信号**，定位程序卡死、启动失败、打不开文件 / 设备、权限异常等问题。 原理：用户态程序访问硬件、文件、网络都要通过内核系统调用，strace 捕获这一层交互。

## 语法

```
strace [参数] 程序名
# 跟踪已经在运行的进程
strace [参数] -p PID
```

## 参数

表格

|优先级|参数|作用|
|---|---|---|
|必须掌握|`-p PID`|附着到正在运行的进程，跟踪它的系统调用|
|必须掌握|`-f`|跟踪目标进程创建的子进程、线程（fork/vfork/clone）；不会自动跟踪外部独立守护进程|
|必须掌握|`-e trace=xxx`|只抓取指定系统调用；简写`-e xxx`多数版本兼容|
|必须掌握|`-o trace.log`|把跟踪日志保存到文件，方便事后分析|
|了解即可|`-tt`|微秒级时间戳，观察调用顺序与时间间隔；**不能直接得到调用耗时**|
|了解即可|`-T`|输出每个系统调用的执行耗时，用于定位慢调用；结果会受 strace 本身开销影响|
|了解即可|`-c`|统计各个系统调用的调用次数、耗时汇总，**不输出每一条详细调用日志**|

## 实战示例

```
# 1. 直接启动程序并跟踪（看程序启动失败原因）
strace ./myapp

# 2. 附着到正在运行进程PID=1234跟踪
strace -p 1234

# 3. 跟踪程序+所有fork/clone生成的子进程/线程，多进程程序常用
strace -f ./myapp

# 4. 只关注文件打开、读写相关系统调用，减少输出干扰
strace -e trace=openat,read,write ./myapp

# 5. 只抓取失败的系统调用（版本依赖，旧板子strace可能不支持）
strace -e status=failed ./myapp

# 6. 查看每个系统调用耗时，定位卡顿点
strace -T ./myapp

# 7. 微秒时间戳，观察调用先后顺序
strace -tt ./myapp

# 8. 汇总统计系统调用次数与耗时
strace -c ./myapp

# 9. 跟踪并将日志写入trace.log，后台慢慢跑，事后分析（多进程必加-f）
strace -f -o trace.log ./myapp

# 10. 附着正在运行进程，同时跟踪它的子/线程，日志保存文件
strace -f -p 1234 -o trace.log
```

## ⚠️ 嵌入式 Linux 重点注意

1. **板子不一定自带 strace**：精简 rootfs 经常不带。需要交叉编译对应架构版本的 strace 放到开发板；架构不匹配会直接报错。
2. 性能开销：strace 拦截每一次系统调用，**显著降低程序运行速度**，生产环境不要长时间挂着跟踪，仅临时调试使用。
3. ptrace 权限：附着其他进程受用户身份、Linux Yama 安全策略、容器配置限制。root 一般权限更高，但仍会存在限制；报`Operation not permitted`不一定是 strace 工具本身故障。
4. 通过返回值与错误码定位故障：
    - `ENOENT`：文件 / 路径不存在
    - `EACCES`：访问权限不足
    - `EBUSY`：资源正忙
    - `EINVAL`：参数无效
    - `ENODEV`：设备不存在或不可用
    - `ETIMEDOUT`：操作超时

> 如果程序卡住，看日志末尾**未返回的系统调用**，如阻塞 read ()、poll ()、futex ()；但阻塞调用只是等待外部事件，不一定就是根本原因。

### 典型调试场景：myapp 打不开 /dev/ttyS1

```
strace -f -o trace.log ./myapp
```

打开 trace.log 搜索`openat`，如果看到： `openat(..., "/dev/ttyS1", ...) = -1 ENOENT` 代表找不到该设备节点，排查方向：路径写错、设备未注册、挂载环境问题。

## 面试背诵要点

strace 用来跟踪进程的系统调用与信号。`strace ./myapp`跟踪新程序；`strace -p PID`附着跟踪已运行进程；`-f`跟踪 fork/clone 产生的子进程和线程；`-e trace=`过滤指定系统调用；`-o`保存日志；`-c`做调用统计。嵌入式板子可能没有预装 strace，跟踪会带来性能损耗；重点看系统调用返回值和 errno，定位文件缺失、权限、阻塞类问题。strace 只能观察系统调用和信号层面的行为，不能直接分析程序内部的 C 函数调用栈；需要分析函数调用、变量和内存状态时，可以配合 gdb 使用。

## 易错坑

- 不加`-f`：只会跟踪父进程，fork/clone 生成的子进程、线程不会被捕获，容易漏掉子进程报错。
- `-tt`只提供时间戳，想看单次调用耗时，需要搭配`-T`。
- `-c`模式只输出汇总统计，不会打印每一条系统调用详情。
- strace 只能捕获系统调用，看不到上层 C 函数逻辑，**不能替代 gdb**。
